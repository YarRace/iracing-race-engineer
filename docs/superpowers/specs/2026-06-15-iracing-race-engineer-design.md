# iRacing Race Engineer — Design Spec

*Дата: 15 июня 2026 · Статус: утверждён, готов к плану*

## 1. Что это и для кого

Персональный инструмент-«гоночный инженер» для iRacing. После заезда анализирует телеметрию + условия трассы + текущий сетап и выдаёт:

1. **Разбор пилотирования** — что менять в стиле вождения;
2. **Рекомендации по докрутке сетапа** — какое поле, в какую сторону, насколько и почему;
3. **Готовый сетап-файл** (`.sto`) — дельта от текущего, с человеческим объяснением каждого изменения.

**Режим владельца:** прототип для себя (Алекс), но архитектурно с заделом под продукт для комьюнити. Каждое решение держит этот баланс: модули сбора данных и дашборда строятся **независимо от Claude Code**, чтобы позже «мозг» переехал с Claude Code на прямые вызовы Claude API без переписывания плумбинга.

## 2. Цель v1 (узко и глубоко)

- **Дисциплина:** GTP (прототип с даунфорсом).
- **Машина:** Cadillac V-Series.R GTP.
- **Трасса:** Watkins Glen.
- **Режим:** только пост-анализ заезда (после стинта).

Одна машина + одна трасса = реально глубокий результат. Расширение на другие машины/трассы — потом, по той же схеме.

## 3. Подтверждённые технические факты (проверено 15.06.2026)

- **Живая телеметрия есть.** iRacing отдаёт данные ~60 Гц через Windows memory-mapped file `Local\IRSDKMemMapFileName`. Зрелые обёртки: pyirsdk (Python), node-irsdk, IRSDKSharper. 200+ каналов.
- **Условия трассы/погоды есть** — секция `WeekendInfo` сессионного YAML (темп. трассы, воздуха, погода).
- **Телеметрия для разбора есть** — температуры шин по зонам, ход демпферов/подвески, газ/тормоз/руль, скорость, рысканье/ускорения.
- **Сетап читается из `.sto`** — формат разобран, есть парсеры (SetupDelta, SetupViewer). Текущий сетап = ground truth по полям и диапазонам.
- ⚠️ **Жёсткое ограничение: SDK только Windows.** Сборщик обязан крутиться на том же ПК, где запущен iRacing. Для v1 это и есть целевая машина (топология — одна Windows-машина, всё локально, сетевой мост не нужен).
- ⚠️ **Открытый риск (единственный):** запись программно-изменённого `.sto`, который iRacing примет. Чтение решено; запись не подтверждена публично. **Разрешается спайком на старте реализации** (см. §7).

## 4. Архитектура — 5 независимых модулей

Всё на Windows-ПК. Модули общаются через файлы/локальный HTTP, каждый тестируется отдельно.

### 4.1. Сборщик (`collector`) — Python + pyirsdk
Фоновый процесс, крутится постоянно.
- Читает живой SDK ~60 Гц: телеметрия + `WeekendInfo` (условия).
- **Две задачи:**
  - (а) **Живой поток** — шлёт урезанный набор (~10 Гц достаточно для экрана) в дашборд.
  - (б) **Запись стинта** — пишет лог текущего заезда в файл. Сам детектит границы стинта (выехал на трассу → бокс/гараж/конец сессии).
- Читает текущий **`.sto`** Кадиллака — базовые значения + список реально регулируемых полей.
- **Самодостаточность:** пишем собственный лог из живого потока, НЕ зависим от того, включил ли пользователь логирование телеметрии iRacing (.ibt).

**Что делает / как использовать / зависимости:** даёт два выхода (живой поток + лог стинта) и сигнал «стинт закрыт». Зависит только от pyirsdk и доступа к папке сетапов.

### 4.2. Дашборд (`dashboard`) — HTML/JS + локальный сервер (FastAPI)
- Открывается в браузере на втором экране. Тёмная тема, крупный шрифт.
- **Шапка:** название + **авто-распознанная связка машина+трасса** (из SDK, см. §4.6) + статус профиля («профиль готов» / «разбор пока не готов»).
- **Зона «онлайн» (во время заезда), справа сверху:** сетка 3×2 — скорость · передача · топливо, под ними круг · дельта · трасса.
- **Зона «температуры шин», слева сверху:** раскладка **2×2 «как на машине»** — LF слева-сверху, RF справа-сверху, LR слева-снизу, RR справа-снизу (подписи «перёд»/«зад»). Каждая плитка: код угла + средняя темп. (цвет: зелёный=ок, жёлтый=тепло, красный=перегрев) + три зоны протектора «вн·ц·нар».
- **Зона разбора (после стинта), снизу:** две карточки — «Пилотирование» и «Сетап → что покрутить» (from→to→почему), + плашка готового `.sto`.
- Терминология: «онлайн», НЕ «живьё».
- **Строится без привязки к Claude Code** → productizable.

**Зависимости:** читает живой поток от сборщика (polling/websocket), связку машина+трасса (§4.6) и файл-результат от объяснителя.

### 4.3. Движок метрик (`metrics`) — Python, детерминированный
Запускается по сигналу «стинт закрыт».
- **Вход:** лог стинта + условия + значения `.sto`.
- **Считает объективные симптомы:**
  - Шины: разброс темп. по ширине (внутр/центр/внешн) на каждом углу, баланс перед/зад и лево/право, горячие давления vs целевое окно.
  - Баланс: признак недо-/избыточной поворачиваемости (угол руля vs боковое ускорение / yaw rate) по фазам — вход / середина / выход.
  - Подвеска: гистограммы хода демпферов, события пробоя / клиренс.
  - Инпуты: эпюры газа/тормоза, трейл-брейкинг, плавность.
  - Стабильность: разброс времён круга, дельты по секторам.
- **Выход:** структурированный «отчёт симптомов» (JSON).
- **Это тестируемое ядро системы** — покрывается юнит-тестами на записанном логе.

### 4.4. LLM-объяснитель (`explainer`) — Claude
Судящий слой.
- **Вход:** отчёт симптомов (JSON) + значения `.sto` + условия + контекст (Cadillac GTP @ Watkins).
- **Выход:**
  - Разбор пилотирования (что менять в вождении);
  - Список правок сетапа — поле → направление → величина → почему, **ограниченный реальными полями и диапазонами из `.sto`** (LLM не выдумывает несуществующие регулировки);
  - Предложенный новый сетап как **дельта** от текущего;
  - Объяснение каждого изменения простым языком.
- **Сменный модуль.** Прототип: Claude Code или Claude API. Продукт: прямой Claude API. Интерфейс модуля стабилен, реализация меняется.

### 4.5. Писатель сетапа (`setup_writer`) — Python
«Механик».
- Накладывает дельту на копию текущего `.sto`, пишет **новый файл с понятным именем** (`cadillacvr_watkinsglen_ai_v3.sto`) в папку сетапов iRacing.
- **НИКОГДА не перезаписывает исходный сетап пользователя** — всегда новый именованный файл.
- За воротами спайка `.sto` (§7). Fallback при провале: точные значения выводятся на дашборд для ручного ввода в гараже.

### 4.6. Авто-определение связки + профили (`profiles`)
**Никаких выпадающих списков машин/трасс.** Текущая связка определяется автоматически из SDK:
- **трасса** — `WeekendInfo.TrackName`;
- **машина** — `DriverInfo` (id текущей машины).
Сборщик читает их при входе в сессию и при смене (новая сессия → перечитать). Дашборд показывает связку в шапке.

**Профиль связки** — это машино/трассо-зависимое знание, без которого разбор поверхностный: эталонные температуры/давления шин, калибровка детектора недо-/избытка, карта поворотов трассы (имена). Поля и диапазоны сетапа НЕ входят в профиль — они берутся из реального `.sto` (авто-адаптация под машину).

**Поведение по связке:**
- Распознана **поддерживаемая** связка (в v1 — только Cadillac GTP @ Watkins Glen) → полный разбор + сетап.
- Распознана **другая** связка → онлайн-телеметрия и базовые симптомы работают, но дашборд честно помечает «разбор сетапа для этой связки пока не готов».

**Масштабирование:** новая машина/трасса = добавить профиль + записать фикстуру стинта. Приложение не переписывается — авто-определение само выбирает нужный профиль. (Это и есть «розетка», заложенная в архитектуре.)

### 4.7. История сессий (`history`) — append-only лог (в v1 только запись)
Каждый разобранный стинт дописывается в `history/sessions.jsonl`: дата, машина, трасса, **условия** (темп. трассы/воздуха, погода), стоявший сетап, симптомы, рекомендации, имя нового `.sto`, времена кругов (best/spread). Ключ — авто-распознанная связка (§4.6).
- **v1:** только логирование — данные копятся с первого заезда (дёшево, оркестратор и так всё это выдаёт).
- **v1.5 (см. §11):** умный слой — при заходе на знакомую связку найти прошлые сессии, **подобрать ближайшую по условиям** (темп. трассы и т.п.) и предложить/подгрузить лучший сетап + прошлые рекомендации. Логировать начинаем сразу, чтобы к v1.5 была накопленная история.

## 5. Поток данных

```
Сборщик ──(живой поток ~10Гц)──> Дашборд (живая зона)
   │
   └──(лог стинта + .sto)
            │  [стинт закрыт]
            ▼
      Движок метрик ──(симптомы JSON)──> LLM-объяснитель
                                              │
                                              ├──(разбор + правки)──> Дашборд (зона разбора)
                                              └──(дельта сетапа)────> Писатель сетапа ──> новый .sto в папку
```

## 6. Обработка ошибок и краевые случаи

- **iRacing не запущен / SDK не подключён** → дашборд показывает «жду iRacing», сборщик переподключается.
- **Короткий/невалидный стинт** (спин, вылет, мало кругов) → движок метрик помечает низкую достоверность, объяснитель смягчает советы.
- **Запись `.sto` провалилась / iRacing отверг** → fallback на ручные значения; исходники не трогаем никогда.
- **Нестандартные/отсутствующие каналы GTP** (гибрид) → деградируем мягко; гибрид/ERS — забота Шага 2.

## 7. Спайк перед реализацией (обязательный первый шаг)

**`.sto` round-trip:** взять текущий `.sto` Кадиллака → программно поменять одно поле → записать новым именем → загрузить в iRacing.
- ✅ Грузит → п.3 (готовый файл) в силе.
- ❌ Отверг → переключаем `setup_writer` в режим «значения на дашборд», п.3 = ручной ввод. Польза сохраняется.

## 8. Тестирование

- **Фикстура реального стинта:** один раз записать реальный заезд на Watkins → сохранить лог → **всю обработку (метрики + объяснитель + запись `.sto`) разрабатывать и тестировать оффлайн**, не сидя в симе каждую итерацию.
- **Движок метрик** — юнит-тесты на этом логе (детерминированный → полностью тестируемый).
- **Спайк `.sto`** — отдельная проверка в симе.

## 9. Стек

Python (`collector`, `metrics`, `setup_writer`) + pyirsdk + FastAPI (локальный сервер) + HTML/JS (дашборд) + Claude (`explainer`). Всё на Windows-ПК.

## 10. Границы v1 — что НЕ делаем

- Только Cadillac GTP @ Watkins Glen, только пост-анализ.
- Без живого коучинга, пит-стратегии, слежки за соперником.
- Эталон-сравнение (Подход 3) — только архитектурная розетка, не реализуем.

## 11. Будущее (Шаг 2 — «живой гоночный инженер во время гонки»)

Зафиксировано, в v1 не входит. Реализуемость части пунктов оценим в процессе.

**v1.5 (ближайший шаг после v1):**
- **Умная подгрузка из истории:** при заходе на знакомую связку найти прошлые сессии (лог из §4.7), подобрать ближайшую по условиям (темп. трассы и т.п.) и предложить/подгрузить лучший сетап + прошлые рекомендации. Само логирование истории — уже в v1.

**Шаг 2 («живой гоночный инженер во время гонки»):**
- **Пит-стратегия:** когда заезжать, сколько лить топлива — с учётом ситуации, аварий, повреждений, числа соперников.
- **Слежка за соперником впереди/сзади:** его темп, дельта, манера; что поменять в *своём* пилотировании, чтобы оторваться или догнать. *Реализуемость под вопросом — разберёмся в процессе.*
- **Живые подсказки по тому, что крутится на ходу:** ABS, ТК, тормозной баланс, мапы двигателя и т.п.
- **Расширение на другие машины/трассы** по схеме v1.
